# 质量检查与故障定位

本文档是验收清单、生产硬门命令和故障定位的唯一事实源。路线专属的编译与抠色规则见
[chroma-video.md](chroma-video.md) 与 [baked-video.md](baked-video.md)。

## 检查顺序

按 Concept Contract 与 Identity Bible 符合性、母版视频、插帧结果、透明帧、稳定帧、
图集、运行时顺序检查。上游素材有问题时，不要在运行时掩盖。

## Concept Contract 回归

每次验收先逐项对照 Concept Contract：

- 主体数量与用户需求一致；用户说“单人”时画面里不能出现第二个人。
- 风格与情绪一致；用户说“动漫”时不能漂移成写实或 CGI。
- 叙事形式一致；演武、拆解、转场各是各的，不互相偷换。
- 背景归属一致：`background_owner=video` 的成品里不允许出现色键残留或抠色处理；
  `background_owner=page` 的成品里不允许烧入页面背景。
- 交互输入与连续性要求一致。
- `clip_continuity` 与 Pilot 批准一致；连续叙事必须为 `chain`，不得用 `independent` 绕过帧链。

任何一项偏离都属于需求级错误：停止生产，回到 Concept Contract 修正，不得将错就错。

## 角色 Identity Bible 验收

有角色时，每张关键帧和每段母版逐项硬验收：

- 同脸：脸型、五官和表情锚点一致。
- 同发型、同发色。
- 同服装：款式、配色、材质一致。
- 同标记：疤痕、配饰、武器、Logo 不增不减不错位。

任一项不符即重做，不接受“差不多”。

## Pilot 硬门

批量生成前确认 Pilot 四项齐全：第一对关键帧、第一段短视频、真实页面最终位置挂载、
用户或视觉验收通过。通过后生成批准文件：

```bash
python3 "$OIL_MOTION/scripts/production_gate.py" approve-pilot \
  --contract source/concept-contract.yaml \
  --identity-bible source/identity-bible.md \
  --first-frame source/K0.png \
  --last-frame source/K1.png \
  --video pilot/pilot.mp4 \
  --page-evidence pilot/page-mounted.png \
  --reviewer visual-review \
  --decision pass \
  --output pilot/approval.json
```

批准文件记录每项工件的 SHA-256，并从合同锁定 `clip_continuity`。生产段由
`video_job.py --stage production` 校验批准文件及工件 SHA-256；缺少、未通过或工件
变化时在联网前阻断。批准后可用 `check-pilot` 复核工件未变化。

## 连续帧链

多段叙事逐段执行帧链规则：

1. 第 `i` 段验收后的实际尾帧就是第 `i+1` 段的首帧输入，不允许只凭原计划图片续接。
2. 提交第 `i+1` 段之前，验证上一段尾帧与本段首帧完全一致并写入清单：

```bash
python3 "$OIL_MOTION/scripts/production_gate.py" verify-chain \
  --previous-tail source/segment-01-last-frame.jpg \
  --next-first source/segment-02-first.jpg \
  --segment-index 2 \
  --manifest qa/frame-chain.json
```

文件大小和 SHA-256 不相同则脚本阻断。`video_job.py --stage production
--continuity-mode chain` 会在联网前再次校验同一清单。

3. 再把第 `i` 段实际尾帧与计划中的 `Ki+1` 做像素与感知对比（可用
   `motion_pipeline.py` 的帧差异分析与接触表对照）；身份、构图或背景偏差超限时，用
   实际尾帧重新约束计划，或重做第 `i` 段，不允许误差逐段累积。
4. 接缝处没有身份、构图、光线或背景跳变；偏差累积时重做对应段，不用程序平滑掩盖。

## 母版视频

- 身份、服装、产品几何和颜色一致。
- 主体没有多余或缺失肢体、道具和结构。
- 主体大小、中心和锚点没有呼吸式漂移。
- 镜头、焦距、透视和光线一致。
- 动作没有停顿、反向、硬切和不必要的待机动作。
- 闭环序列首尾姿态一致。
- chroma 路线：色键背景四角和时间维度均匀。
- baked 路线：场景、环境光、地面接触和景深连续，无色键残留。

## 插帧结果

- 必须同时查看原始帧和插帧后的编号接触表。
- 目标帧率与 Motion Brief 一致，默认 48 FPS。
- 没有重影、双轮廓、边缘撕裂、部件穿插或结构扭曲。
- 插帧没有增加空帧、亮度闪帧、大小突变和中心突变。
- 自动报告通过不代表人工验收通过；发现伪影时停止，不得跳过插帧直接交付原帧。

## 抠图结果

- 视频路线只验收最终 H.264 MP4 解码出的帧，编码前 PNG 只能用于上游诊断。
- 图像模式为 RGBA。
- 四角 alpha 为 0。
- 头发、眼镜、线稿、耳朵、尾巴和细小道具完整。
- 边缘没有绿色或洋红溢色；主体内部白色和半色调没有被误删。
- 相邻帧 alpha 边缘没有明显跳动。
- 白、黑、洋红测试底色以及目标页面真实背景上的合成验收全部干净。

chroma 路线的逐帧抠色硬检测、拒收规则和 `compile.json` 验收字段见
[chroma-video.md](chroma-video.md) 的“抠色硬门”；检测不通过或人工发现缺陷时按该节
拒收母版。

### 视频路线硬门槛

`compile_scroll_video.py` 会用 `compile.json.runtime.keying` 对桌面和移动成片重新抽帧抠色，
并写入 `qa/post-encode-keying.json`。以下任一项超限都停止交付：

- `keyLikeAlphaP99`：色键样本的 99% Alpha，拦截整块半透明绿幕。
- `visibleKeyPixelRatio`：仍可见的色键优势像素比例。
- `opaqueKeyPixelRatio`：仍接近不透明的色键优势像素比例。
- `edgeKeyDominanceP95`：半透明边缘去溢色后的残留通道优势。

还必须查看白、黑、粉、蓝背景矩阵。Canvas 阴影、滤镜和混合模式只能在抠像完成后作用于
独立合成层，不能直接放大原始视频边缘残色。

## 分析报告

`motion_pipeline.py analyze` 会报告：

- alpha 包围盒、主体中心、占用率和亮度。
- 相邻帧差异。
- 尺寸突变、中心突变、亮度闪烁、空帧和近重复帧。

警告是定位线索，不是自动删帧指令。缓慢动作可能产生合理的近重复帧。

## 图集验收

- 清单中的 `frameCount`、`columns`、`rows` 和实际图集一致。
- 每个单元格只含一个完整帧，空余单元格透明。
- 图集不超过目标设备纹理限制。
- 接触表中的帧顺序与交互参数方向一致。

## 运行时验收矩阵

至少测试：

- 桌面鼠标慢速、快速、连续反向和绕主体一圈。
- 页面滚动后鼠标不动。
- 窗口缩放和横竖屏变化。
- 手机触摸和陀螺仪允许、拒绝、不可用三种情况。
- 冷缓存、慢网、资源加载失败。
- `prefers-reduced-motion`。
- 页面切后台后恢复。
- 快速反复移动输入时不粘滞、不抽动、不越界；低速跟随自然，高速转向受限但不明显落后。
- 在目标 DPR 的实际 CSS 尺寸下清晰，浏览器 100% 页面缩放检查真实渲染，不以原视频或接触表代替。

## 常见问题

### 某个角度闪一下

依次检查：

1. 母版是否存在单帧亮度或形变异常。
2. 文件名是否按数字而不是字符串顺序排列。
3. 图集单元格尺寸、列数和帧数是否与运行时一致。
4. 环形起始角是否映射错位。
5. 最后一帧到第一帧是否真的连续。
6. 是否有图片层交叉淡化或旧帧未移除。
7. 图集是否尚未完成解码就开始换帧。

### 头或产品大小会变化

- 优先重新生成并强调固定比例、固定镜头和固定锚点。
- 固定身体的朝向动画可以使用 `normalize` 小幅稳定。
- `max-scale-change` 保持克制；过度稳定会让轮廓抽动。
- 自由动作、镜头推进和真实透视变化不要稳定。

### 动画粘滞

- 不要层层叠加多个 lerp。
- 使用有速度状态的 `smoothDamp`。
- 适当降低 `smoothTime`，同时提高 `maxSpeed`。
- 确认目标帧每次输入都更新，没有过大的输入死区。
- 快速移动时不要等待图片请求；所有随机访问帧应已预加载。

### 动画太快、不自然

- 限制最大帧速度。
- 保留速度状态，不要直接把当前帧设为目标帧。
- 动作母版要有连续中间姿态；缺帧不能只靠减速修复。

### 首次移动出现虚影

- 不使用两张帧的透明交叉渐变。
- 初始帧必须来自同一图集。
- 等待图集解码完成后再允许交互。
- 初次输入从当前帧平滑追踪目标帧。

### 新版本变糊

- 检查母版分辨率是否下降。
- 检查切帧或稳定时是否重复缩放。
- 检查图集单元格是否小于实际显示尺寸。
- 检查 WebP 质量、是否使用有损透明压缩和浏览器缩放倍率。
- 从高分辨率母版重新构建，不从网页图集反向提取。

### 滚动后指向错误

指针屏幕坐标没有改变，但主体的屏幕位置改变了。滚动时必须重新读取主体矩形并重新计算相对向量。

## 建议预算

预算应按项目调整，以下只是首轮参考：

- 首屏动画压缩资源尽量控制在 1–4 MiB。
- 首屏关键素材总等待上限 4–6 秒，并提供静态降级。
- 图集尺寸尽量不超过 4096×4096。
- 实际显示尺寸不超过源单元格尺寸；高 DPR 屏幕预留约 2 倍像素。
- 循环中不发生网络请求，不因同一帧重复写 DOM。
